# Internationalization (i18n)

The UI is translatable (English + German today) via `i18next` + `react-i18next`. This doc covers the architecture, key conventions, and the two worked examples you'll need when extending it: adding a language, and adding a date/number format profile.

## Two independent axes

UI language and date/number format are **separate, independently selectable preferences** — not one combined locale selector.

| Axis | Values | Default | Drives | Persist key |
|---|---|---|---|---|
| **UI language** | `en`, `de` | browser language, falls back to `en` | `t()` strings; MUI **core** theme locale (`@mui/material/locale`); date picker **`localeText`**; `<html lang>` | `cetrack:lang` |
| **Date/number format** | `iso`, `de`, `us` | **`iso`** | `formatDate`/`formatDateTime`/`formatNumber`; date picker **`adapterLocale`** + first-day-of-week | `cetrack:dateFormat` |

Why split them: the app has always displayed ISO dates (`yyyy-MM-dd`) regardless of language, and that's a deliberate choice worth preserving as its own option — a German-speaking user may still want ISO dates, an English speaker may want German-style dates. Bundling the two into one locale selector would force false choices.

The MUI date picker's two locale inputs map one to each axis:
- `adapterLocale` (date-fns parse/format/first-day-of-week) follows the **format** axis.
- `localeText` (translated button/aria strings like "Clear", "Today") follows the **language** axis.

## Architecture

- **`src/i18n/index.ts`** — bootstraps i18next synchronously (no Suspense) with inlined `en`/`de` resources, detects the initial language (`localStorage` → `navigator.language` → `en`), and persists on `languageChanged` (also updates `document.documentElement.lang`).
- **`src/i18n/locales/en.json`, `de.json`** — the single translation namespace, nested by section (see key conventions below). `de.json` must stay key-for-key identical to `en.json` — enforced by `src/i18n/locales.test.ts`.
- **`src/i18n/i18next.d.ts`** — types `t()` against `typeof en`, so a typo'd key is a compile error.
- **`src/i18n/formatProfile.ts`** — the format-axis mapping (`FormatProfile = 'iso' | 'de' | 'us'` → date-fns locale + `Intl.NumberFormat`), plus a **module-global** getter/setter (`getFormatProfile`/`setFormatProfile`) so plain functions like `formatDate` can read the current profile without being hooks.
- **`src/hooks/useLanguage.ts`** — thin wrapper over `useTranslation()`; i18next is the single source of truth, there's no separate language context/provider.
- **`src/hooks/useDateFormat.ts`** + `DateFormatProvider` (in `App.tsx`) — mirrors the existing `useColorMode`/`ColorModeProvider` pattern: React state seeded from `localStorage`, the setter persists and also updates the `formatProfile.ts` global.
- **`src/components/layout/LanguageSwitcher.tsx`**, **`FormatSwitcher.tsx`** — icon-button + menu, mounted in `AppShell`.

### Why a format-only change still re-renders the UI

`formatDate`/`formatNumber` are plain functions reading a module global, not hooks — so switching the format profile doesn't by itself trigger React to re-render anything. To make it work, `ColorModeProvider` (in `App.tsx`) subscribes to **both** `useLanguage()` and `useDateFormat()` and folds `lang` and `dateFormat` into its theme `useMemo` deps. A profile change recreates the theme object, which changes the `ThemeProvider` value, which re-renders the whole tree — and every formatter call along the way reads the now-current global. This is intentional and covered by `FormatSwitcher.test.tsx`.

## Key conventions

- **Naming**: `<section>.<component>.<key>`, camelCase — e.g. `bikes.form.createdSuccess`, `components.mount.atLabel`.
- **Reuse across features**: generic, identical-text concepts (Name, Manufacturer, Purchase Date, Cancel, Save, Delete…) live under `common.*` rather than being duplicated per feature. Feature-specific wording stays under its own namespace even if two features happen to share a word.
- **Enum/status leaves keep backend spelling**: `errors.TYPE_MISMATCH`, `errors.MOUNTING_GOVERNED` — these are backend error codes, not prose.
- **Interpolation**: `{{name}}` — `t('common.deleteConfirmMessage', { name: bike.name })`.
- **Plurals**: `_one`/`_other` suffixes + a `count` variable — i18next picks the form automatically:
  ```json
  "autoClosedNotice_one": "Mounted — auto-closed {{count}} previous mounting",
  "autoClosedNotice_other": "Mounted — auto-closed {{count}} previous mountings"
  ```
  ```ts
  t('components.mount.autoClosedNotice', { count: changes.closed.length })
  ```
- **Never call `t()` at module scope** — it freezes to whatever language was active when the module first loaded. Module-level arrays (nav entries, onboarding steps, landing guide steps) store a `labelKey`/`titleKey`/`bodyKey` (typed as `ParseKeys` from `i18next`) and translate at render time inside the component.
- **Zod validation messages**: schemas are built by a `buildSchema(t: TFunction)` factory, memoized with `useMemo(() => buildSchema(t), [t])` before `zodResolver(schema)` — so switching language re-derives validation messages. See `ComponentForm.tsx` for the canonical example.
- **Extract verbatim**: don't reword strings while extracting them, so text-literal test assertions (`screen.getByText('...')`) stay green without touching the test files.

### Adjusting an existing translation

Translations are just JSON — edit the value in both `en.json` and `de.json` (the key-parity test only checks that the *keys* match, not the wording):

```diff
- "addButton": "Add bike",
+ "addButton": "Add a new bike",
```

No code change needed unless the key itself changes.

## Worked example: adding a language (French)

1. Create `src/i18n/locales/fr.json` as a copy of `en.json` (same keys, French values). Keep the plural suffixes (`_one`/`_other`) — French pluralization matches i18next's default `Intl.PluralRules` behavior for `fr` automatically.
2. Register it in `src/i18n/index.ts`:
   ```ts
   import fr from './locales/fr.json'
   // ...
   resources: {
     en: { translation: en },
     de: { translation: de },
     fr: { translation: fr },
   },
   ```
   Also extend `AppLanguage` to `'en' | 'de' | 'fr'` and the `detectLanguage()`/`appLanguage()` checks.
3. Extend `src/i18n/i18next.d.ts`'s `CustomTypeOptions` if it enumerates languages explicitly (it currently types against `typeof en`, so no change needed there as long as `fr.json` has the same shape).
4. Add an entry to `LanguageSwitcher.tsx`'s `LANGUAGES` array: `{ value: 'fr', label: 'Français' }` (language names in the switcher are shown in their own language, untranslated — see the existing `English`/`Deutsch` entries).
5. Compose the MUI **core** locale in `App.tsx`'s `ColorModeProvider`: import `frFR` from `@mui/material/locale` and extend the `lang === 'de' ? createTheme(base, coreDeDE) : base` branch.
6. Compose the MUI **picker** locale in `App.tsx`'s `LocaleProviders`: import `frFR` from `@mui/x-date-pickers/locales` and extend the `lang === 'de' ? deDE.components... : undefined` branch.
7. Run `npm test` — the locale key-parity test (`src/i18n/locales.test.ts`) will fail loudly if `fr.json` is missing or has extra/missing keys relative to `en.json`.

## Worked example: adding a format profile

Say you want a fourth profile, e.g. `uk` (UK date order, still comma-grouped numbers):

1. Extend the union in `src/i18n/formatProfile.ts`:
   ```ts
   export type FormatProfile = 'iso' | 'de' | 'us' | 'uk'
   ```
2. Add it to both mapping tables in the same file:
   ```ts
   const DATE_FNS_LOCALES: Record<FormatProfile, Locale> = { iso: sv, de, us: enUS, uk: enGB }
   const NUMBER_LOCALES: Record<FormatProfile, string> = { iso: 'en-US', de: 'de-DE', us: 'en-US', uk: 'en-GB' }
   ```
3. Add an entry to `FormatSwitcher.tsx`'s `PROFILES` array: `{ value: 'uk', label: 'English (UK)' }` (again, untranslated — these are format names, not UI strings).
4. Extend the validation in `App.tsx`'s `initialFormat()` (`stored === 'iso' || stored === 'de' || stored === 'us' || stored === 'uk'`) so a stale/invalid `localStorage` value still falls back safely.
5. Add test cases to `src/utils/formatters.test.ts`'s format-profile `describe` block asserting the new profile's date and number output.

## Persistence

- `cetrack:lang` — one of the registered language codes, read by `detectLanguage()` in `src/i18n/index.ts`.
- `cetrack:dateFormat` — one of `FormatProfile`, read by `initialFormat()` in `App.tsx`.

Both keys mirror the pre-existing `cetrack:colorMode` pattern (plain string in `localStorage`, no serialization).

## Testing notes

- `src/setupTests.ts` pins the language to `en` (`i18n.changeLanguage('en')`) and the format profile to `iso` before each test file runs, so all pre-existing English/ISO text assertions keep working unmodified.
- When testing a component that reads `useDateFormat()` outside of `App.tsx`'s `DateFormatProvider`, wrap it in `<DateFormatContext.Provider value={...}>` directly (see `FormatSwitcher.test.tsx` for the pattern) rather than importing the provider itself, since it's not exported.
- Switcher tests reset both `localStorage` keys and the active language/profile in an `afterEach`, since `setupTests.ts`'s global `afterEach` only runs React Testing Library's `cleanup()`.
